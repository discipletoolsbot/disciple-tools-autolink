# Porting features from the abandoned 2.0 branch

Working document. Tracks work from the `2.0` branch that we want on `master`.

## Background

`origin/2.0` is a **complete from-scratch rewrite** of Autolink onto CodeZone's
"modern disciple.tools plugin starter template" (PSR-4 `DT\Autolink\` in `src/`,
league/route + middleware + DI container, Vite, PHP-Scoper vendor isolation).

**We are not adopting that framework** — it is effectively abandoned
(`thecodezone/wp-router` untouched since Sept 2024), so 2.0 is being treated as a
**parts donor, not a branch to merge**.

Key facts to re-establish context in a later session:

- `git merge-base origin/master origin/2.0` returns **nothing**. The two branches
  have **unrelated histories**. `git cherry-pick` will not work — see
  [How to port](#how-to-port) below.
- Branch tips at time of writing: `origin/2.0` = `bcc6933`, `origin/master` = `65ec47f`.
- Tags: `2.0.0-rc.5` = `bcc6933` (last), `2.0.0-rc.4` = `a5f7016`, `2.0.0-beta7` = `e0bf05f`.
  All 2.0 releases are marked **Pre-release**; `1.0.11` (Feb 2024) is still the only "Latest".
- Both branches have been dormant since ~1 March 2025. `master` since April 2024 is
  ~60 commits of Weblate translations, dependabot and CI path fixes only — **no feature work**.
- 2.0 never shipped. Likely blocker: its bootstrap calls
  `Dotenv::createUnsafeImmutable( __DIR__ )->load()` with no try/catch, while `.env`
  is **not** in the release zip's `cp -r` list → should fatal on activation.
  (Hypothesis, untested. rc.1–rc.5 were five release attempts in four days.)

## How to port

Cherry-pick does not work across unrelated histories with different file layouts.
The workflow is: read the diff, then hand-apply to master's equivalent file.

```bash
git show <hash>              # read the change
git show origin/2.0:<path>   # read a whole 2.0 file
```

Most of the value is in the **JS / CSS / view layer, which is not coupled to the
CodeZone framework**. 2.0's components map almost 1:1 onto master's files.

### Naming differences to translate when porting

- Custom element prefix: 2.0 uses `al-*`, master uses `app-*` (e.g. `al-church` → `app-church`).
- Localized JS global: 2.0 uses a single `$autolink` object; master uses `app` (from
  `wp_localize_script(... 'app' ...)`) plus `magic` (parts / rest_namespace).
- API URL helper: 2.0 `api_url('field')`; master `window.app.rest_base + window.magic.rest_namespace`
  with an `action` key in the POST body.
- Option keys: 2.0 renamed the prefix `disciple_tools_autolink_*` → `dt_autolink_*`.
  **Keep master's keys** when porting so existing settings survive.
- 2.0 uses lit decorators (`@customElement`, `@property`). Master's babel config supports
  them today, but see the lit 3 caveat under [Prerequisite](#prerequisite).

## Prerequisite

**2.0 does NOT fix the web components problem.** It pins
`@disciple.tools/web-components: ^0.5.2` exactly like master, and its `_church.js`
uses the same 0.5.2 `handleSave(group_id, {health_metrics})` API. The theme now ships
1.0.2, where `DtChurchHealthCircle` extends `DtMultiSelect` and takes `.options` / `.value`.

Separate work, already drafted and currently in `git stash` ("initial bug fixes"):
switch the plugin to consume the theme's `DtWebComponents` global via webpack
`externals`, upgrade lit 2 → 3, and migrate the health circle to the new API.
That lit 3 upgrade is why the stashed work converted the decorator-using files to
`static get properties()` — decorator semantics differ between lit 2 and 3.

Several ports below touch the same files, so sequence that work first or alongside.

**Status: done**, on `feat/web-components-1.0-church-counts`, alongside item #1.

#### Notes for #1 (reactive church health counts) — done

Landed on `feat/web-components-1.0-church-counts`, together with the web components
migration described under [Prerequisite](#prerequisite), because they are the same change.

- New `magic-link/js/church-counts.js` defines `app-church-counts`; `magic-link/js/churches.js`
  renders it instead of building the count markup inline, and the document-level `change`
  listener in `magic-link/magic-link.js` is gone.
- `templates/parts/health-counts.php` was **deleted**. It was dead: nothing included it, and
  the app has rendered counts from `churches.js` for as long as master's history shows.
  The earlier claim in this document that master renders the counts in PHP was wrong.
- The commits originally cited for this item do not belong to it. `666ae5e` only *downgrades*
  `@disciple.tools/web-components` from `^0.6.9` to `^0.5.2`; `164a2f2` retitles a `dt-tile`
  in `resources/views/groups/modal.php`, which belongs to item #5. `ed6b9b3` deletes one line
  from a dom-hook we did not port. The real source is `_church-count.js` at the 2.0 tip.
- **Why the badges had vanished in the earlier draft:** `dt-modal` rendered
  `<slot name="openButton">` in web components 0.5.2 and dropped it in 1.0. The icon and badge
  lived in that slot, so they stopped being rendered at all. `app-church-counts` now renders its
  own trigger button and opens the modal by dispatching `open` at it. The modal also gained the
  group name as its title and a Close button, since `hideHeader` with no `closeButton` leaves a
  1.0 modal with no visible way out.

Verified on dtplayground: badges render, the modal opens and closes, edits update the badge
without a reload, and both `member_count` and `health_metrics` persist through the magic-link
endpoint.

#### Notes for #4 (hide genmap / coaching tree)

Don't follow `cdaa077` literally — the feature was partly dismantled afterwards.

- At the **2.0 tip the whole thing lives in the view**:
  `resources/views/partials/tools-menu.php` wraps the entire tab bar in
  `if ( $groups['total'] >= 1 )`, using a `DT_Posts::list_posts( 'groups', [ 'assigned_to' => [ get_current_user_id() ], 'limit' => 1 ] )` lookup.
- `src/Middleware/HasGroups.php` still exists at the tip but is **never referenced**
  by `routes/`, `src/` or `resources/` — dead code. `src/Conditions/HasGroups.php`,
  added by the same commit, was **deleted**. Don't port either.
- The two disagree on the threshold: the view shows the tabs at `total >= 1`, the
  orphaned middleware redirected away at `total <= 1` (i.e. it also bounced users who
  had exactly one group). Pick our own rule deliberately.
- 2.0's view hides the **entire** tab bar — including "My Groups" — not just the genmap
  and coaching tree. Decide whether we want that or only the two.

On master this is a small change: guard the buttons in
`templates/parts/church-view-tabs.php`, and if we also want to block direct URL access,
guard the `tree` and `genmap` cases in `magic-link/user-app.php` `routes()`.

## Separately: bugs found on master while investigating

Not from 2.0 — found by reading master. Listed here so they aren't lost.

- `controllers/controller.php:36` — stray literal `' controller.php'` concatenated into
  the translated `view_church_label` string.
- `controllers/controller.php` `global_data()` — the `is_wp_error( $result )` checks are
  inverted (`$result` is never assigned), so `$data['churches']` is always emptied.
- `controllers/survey.php:19` — `show()` pre-fills answers with `get_user_meta()` but
  `process()` writes with `update_post_meta()`, so previous answers never appear.
- `magic-link/user-app.php:103-110` — after checking `is_user_logged_in()`, it calls
  `wp_set_current_user( $this->parts['post_id'] )` with no check that the magic key
  belongs to the logged-in user. Any logged-in user holding another leader's app URL
  acts as that leader for the request.
